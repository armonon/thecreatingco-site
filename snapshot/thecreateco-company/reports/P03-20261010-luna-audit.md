## Findings

1. **Confirmed recovery limitation (not evidence that valid work is silently replaced):** autosave is a single IndexedDB record (`current`) overwritten per save; there is no prior-good snapshot/version history. `src/lib/idb.ts:1-4,28-43`. A syntactically corrupt autosave is caught on startup and not loaded (`src/pages/Studio.tsx:96-109`), but after `loaded` becomes true the fresh initial project is autosaved after 800 ms (`src/pages/Studio.tsx:117-124`), overwriting the corrupt record. This avoids installing unparsable JSON, but offers no recovery UI/backup if the only saved record is corrupt. No browser-level corruption scenario was run.

2. **Confirmed shallow validation gap for `.animate` and Locker project opens:** `deserializeProject` only JSON-parses and checks truthiness of `version`, `layers`, and `timeline`; it does not validate their types/content or supported version (`src/engine/project.ts:65-70`). The file and Locker handlers install any accepted object directly into the active project (`src/pages/Studio.tsx:73-80,319-331`). Thus malformed-but-truthy structures can pass and replace the current in-memory project, then break rendering/autosave. Parse failures and objects missing those three fields are rejected; file-open errors alert, whereas the Locker callback has no local error handling. The source audit itself did not run a browser repro; focused malformed-fixture tests were added and pass below. The parent separately reproduced this malformed-import crash in browser.

3. **Confirmed reference-video reopen loss:** serialization inlines `blob:` sources as data URLs (`src/engine/project.ts:41-63`), preserving reference bytes in the saved JSON under ordinary successful fetch/read. But reopening installs project layers without rebuilding video elements (`src/pages/Studio.tsx:73-80,96-109,319-331`); video rendering requires a `videoElements` entry (`src/engine/render.ts:48-57`) and those are only registered by the fresh-import/Locker-media paths (`src/pages/Studio.tsx:165-173,250-264`). Therefore a saved/reopened video reference is present in the project JSON but not rendered/exported after reopen. Image data URLs are consumed by the image rendering path; they are not evidence of the same gap.

4. **Undo/redo absent in inspected implementation:** no undo/redo/history implementation or controls found in `src/pages/Studio.tsx` or engine source. Edits update React project state directly; e.g. stroke commits append in place of a history operation (`src/pages/Studio.tsx:192-202`). This is a confirmed feature gap by source search, not a runtime test.

5. **Potential stale autosave write (hypothesis, un-reproduced):** debounce cleanup only cancels a not-yet-fired timer; a serialization/IndexedDB write already underway is not sequenced or invalidated (`src/pages/Studio.tsx:117-124`, `src/lib/idb.ts:30-38`). Concurrent blob conversion/storage could complete out of order and leave an older snapshot last. No deterministic repro was run.

## Narrow next step

Implement and test strict project-schema/version validation before any state replacement; add a recovery-safe autosave strategy that preserves the prior valid snapshot until a candidate parses/validates, with explicit corrupt-autosave recovery behavior. Separately rehydrate video references from persisted data URLs on every project-open path (and clean up replaced media resources), and add an undo/redo history for project mutations. First regression targets: malformed `.animate` and Locker payload leave current project untouched; corrupt autosave leaves recoverable prior data; valid image/video references survive save-close-reopen-export; undo then redo restores exact project JSON/reference state. Add serialized autosave ordering test if reproduction confirms the race.
